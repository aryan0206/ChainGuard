### Project identity and research position

**Problem.** A supported MCP tool proposal may be individually innocuous while its authorization or sensitivity meaning depends on earlier reads, grants, revocations, and use of a one-use permission. A detector finding also needs evidence that an independent assessor can inspect without trusting the submitted package's own key, configuration, or description of events. ChainGuard studies both questions on a controlled local stdio tool surface.

**Bounded gap.** Related work already has contextual MCP enforcement (Wang et al.), declarative runtime constraints (AgentSpec), capability/data-flow controls (CaMeL), and authenticated sequenced logs (signed syslog). The gap pursued here is a controlled, independently labeled comparison of current-event (B0), conservative unordered-prefix (B1), and ordered-state (B2) representations under a frozen common policy, coupled to separately checked audit authenticity, finding reproduction, and fresh complete-run acceptance. The [paper's related-work and research-gap sections](overleaf-evaluation1/main.tex) and [charter](PROJECT_CHARTER.md) support this framing. It is a methodological question, not a claim that earlier systems lack session context.

**Role and boundary.** ChainGuard is a research testbed and bounded security monitor for a configured MCP stdio proxy, scripted client, controlled tools, trusted host context, and synthetic data. It is not a general MCP gateway, arbitrary information-flow tracker, or demonstrated real-LLM defense. The proxy and M6 host control dispatch; B0/B1/B2 findings remain distinct from execution authority and independently observed ground truth. Observation mode does not bypass authorization; the explicitly configured synthetic local-sink override is a separate bounded exception. See [Architecture Lock §§2–4, 15–20](ARCHITECTURE_LOCK.md) and the [threat model](THREAT_MODEL.md).

**Implementation contribution.** The repository implements supported client/proxy/server mediation; deterministic representation evaluators and B2 reference/streaming agreement checks; a trusted M6 host with scoped grant/revoke/one-use reservation, default-deny unauthorized release, and synthetic sink witnesses; durable proposal/decision/intent/outcome records; canonical SHA-256 chain and ECDSA P-256/SHA-256 signed closure; offline structural, pinned-key, context, lifecycle, and finding checks; and an independently registered expected-run acceptance registry with durable duplicate rejection. Exact persisted-batch readback precedes forwarding in the audited path. Signing authenticates a commitment, reproduction checks consistency with the frozen detector/policy, and acceptance decides evidence eligibility; none alone establishes observational truth, benign behavior, trusted time, or prevention of tool-execution replay. The [current claims register](CLAIMS_REGISTER.md), [results ledger](RESULTS_LEDGER.md), and M6 [live runtime](../chainguard/m6_live_runtime.py), [audit](../chainguard/m6_live_audit.py), [verifier](../chainguard/m6_live_verifier.py), and [acceptance registry](../chainguard/acceptance.py) bound these claims.

**Research contribution status.** The specified contribution is a reproducible method for comparing representation sufficiency and enforcement consequences, and for separating evidence integrity, authenticity, finding reproduction, and task-bound acceptance under manipulation. The final empirical result is still unestablished: the current [ledger](RESULTS_LEDGER.md) classifies every E01–E13 experiment as lacking a fully contract-qualified research result. M6Q cases, E08 conformance, engineering tests, and the E03 contract-incomplete pilot must not become research denominators or detector-superiority claims. The [paper](overleaf-evaluation1/main.tex) is an Evaluation-1 snapshot and predates the newer bounded M6 qualification; use the ledger for current status rather than silently treating the paper's older pending-M6 language as current.

**Defensible professor-facing novelty statement.** “ChainGuard contributes a controlled MCP testbed and evaluation method that compares exactly what current-event, unordered-history, and ordered-state policies can decide on the same specified workflows, then links each decision to signed, independently inspectable evidence and a separately checked expected-run submission. The engineering integration is demonstrated in bounded local workflows; whether it improves decisions or cost against alternatives remains an open empirical question.” This claims no new cryptography, first session-aware defense, first signed agent trace, general superiority, or finished study.

### Exact execution terminology

Call the project a **system and research testbed** with several connected but differently qualified workflows. The M4 demonstration is an **integrated, non-release live workflow**: scripted MCP input reaches the stdio proxy and controlled tools; audited transactions and outcomes are persisted; clean closure seals a package; a separate process inspects it. The M1 client command exercises mediation only. M2 fixture replay evaluates representations and prewritten oracle expectations without executing tools or committing live audits. M5 acceptance is an assessor-side workflow, not proof of benign execution. M6 provides a bounded live permission/release/evidence workflow through the trusted host and qualification harness, including recorded current-source M6Q cases and reinspection; it is not a stable public single-command demonstration or a completed E06/E07 research experiment. Therefore do not call the whole project one complete end-to-end research pipeline. Never call replay “live,” or M6Q engineering checks “research experiments.” Refer to M6 as **M6**; “Phase 2” is a separate historical workflow/oracle foundation label, not its replacement.

### Connected pipeline map and first-time explanation

```text
M1: SDK client → stdio proxy → controlled echo/failure server → checked client JSON
M2: frozen fixtures → staged admission/history → B0/B1/B2 → independent fixture oracle → replay JSON
M3: scripted MCP frames → proxy → typed SQLite append → controlled server → outcomes/journal
M4: scripted MCP frames → audited proxy/SQLite → clean closure/P-256 signed package
                                                 → new-process offline verifier
M5: pre-register complete-run expectation → M4 path → signed package → durable accept/reject
M6Q: pre-register + host controls/raw MCP calls → reservation + audit → child/local sink
                                                   → signed export → separate inspect → acceptance
       M6Q-08: separately injected pre-dispatch audit failure → halt/no signed export
```

M1's client is not fed into M4 or M6; their harnesses construct their own protocol frames. M2's replay history is not an M3/M4/M6 live observation stream. M3 and M4 share the supported non-release proxy surface, but M4 is a separate signed path. M5's campaign actually calls M4, so that connection is real. M6's trusted host path is separate from the M1–M5 relay and uses a controlled synthetic source/sink surface. B0/B1/B2 are deterministic shadows; the controller owns actual authorization and one-use consumption. The signed package verifies what was committed and reproducibility of findings; the assessor sink/host/child witnesses are distinct observations needed to assess actual effects. A P-256 signature does not prove detector correctness, full capture or trusted time.
