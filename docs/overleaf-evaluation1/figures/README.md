## Assumptions and precision

- Figure 1 depicts the implemented local stdio path. The live surface is public, non-release echo / controlled_failure. B0/B1/B2 findings are shadows in this slice. It does not claim live sensitive-release enforcement, live grant/revoke/consumption, a live sink collector or a fully qualified live five-dimensional oracle. The Independent Oracle lane summarizes the fixture/assessor contract; current lifecycle/sink examples are replay-only. The oracle has no arrow into detection or control. The return annotation summarizes separate outcome persistence followed by committed-history updates.
- Figure 2 preserves the requested GRANT → USE → REVOKE → PROPOSE RELEASE and GRANT → REVOKE → USE → PROPOSE RELEASE strings as schematic illustrations. They are not asserted to be an executed or valid opposite-label E02 pair. USE means once-only projection of a selected grant in committed dispatch intent, not tool arrival or a denied proposed use. A same-scope USE after revocation cannot consume a revoked grant. It requires a separately valid available/NEW grant; extra eligible facts must participate in the locked projection. An override has an empty selection and generates no USE. B1 equality requires identical complete permitted projections and current calls, not counts alone. B2 retains order, but different transitions need not yield different final labels. Correctness comes from independent fixture/oracle labels.
- Figure 3's canonical-record/hash-chain lane expresses data dependencies, not a second post-execution hash computation. Candidate bytes/hashes are prepared before the transaction, checked by exact readback and become trusted only after confirmed COMMIT. Clean closure freezes trusted values and validates one exact snapshot before signing. INSPECT and M5 fresh whole-run acceptance are separate from forwarding. Schema/readback failures halt after rollback; ambiguous execution COMMIT halts without retry/adoption/forwarding. Required readback covers the full new batch and exact manifest, not continuous protection of every old row.
- Figure 4 currently uses the qualitative labels “trusted count advanced” and “required records suppressed or altered” to show the trusted-state/storage mismatch. The earlier requested 17/15 illustration is historical and is not a measured result or a label in the current SVG/PDF assets. The documented flaw, forwarding impact and repair are AF-001; no cryptographic forgery is claimed. The repair closes the pre-forwarding gap under SQLite/runtime assumptions. It cannot undo prior tool effects or prevent arbitrary post-commit database mutation.
- Figure 5 groups all thirteen exact protocol names for readability, not scheduling. E01–E13 remain unexecuted as final empirical experiments. E06, E08 and E12 have missing prerequisites; E08 conformance is pending. Protocol authority ambiguities must be resolved before affected experiments. M6 remains mandatory for final completion.

Each figure introduces no component, transport, cryptographic algorithm, methodology change or supported research claim beyond the locked architecture/protocol. No superiority, novelty, accuracy, cost, trusted-time, universal protection, tamper-proofing or real-world truth claim is made. Signatures authenticate committed evidence; reproduction checks consistency; acceptance checks evidence eligibility and may accept evidence containing security violations.
