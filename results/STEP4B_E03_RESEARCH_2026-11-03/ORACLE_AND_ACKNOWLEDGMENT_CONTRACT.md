# Independent oracle and task acknowledgment — proposed contract

**Design only; implementation and use require approval.** This applies to the proposed [cohort](COHORT_DESIGN.md) and [exact sample](SAMPLE_PLAN.md), not to the historical pilot. The [gap assessment](COLLECTION_GAP_ASSESSMENT.md), [approval list](OWNER_APPROVALS_REQUIRED.md), and [summary](STEP4B_SUMMARY.md) state the execution gate.

## Independent labels

Before any execution, an assessor separate from detector output freezes case ID, parent/task objective, resource, tool, exact bytes, declared decoding, scope, grant/control order, expected predecision authorization and expected effects in an assessor-held, digest-pinned inventory. The assessor uses trusted registry/tool contracts, independently observed source results, host control admission and **confirmed** reservation/commit witnesses, raw proposals and pre-reservation permission snapshots. For a proposed send, the assessor compares the exact destination and raw/decoded synthetic canary under the frozen decoder; the source witness must show actual prior successful exposure. The assessor must not inspect B0/B1/B2 predictions when assigning or resolving labels. The controller's decision and the audit journal cannot substitute for this oracle.

Immediately before each proposal, the assessor records AUTHORIZED, UNAUTHORIZED or INDETERMINATE with `case_id`, `parent_id`, `task_id`, `request_id`, rule/contract basis, evidence path+digest references, assessor identity, decision time/order and any disagreement. A second blinded assessor can review predecision records; disagreement is resolved against the frozen contract and independent observations, with both original judgments retained. If facts remain missing or disputed, use INDETERMINATE and exclude from binary correctness, never relabel from a detector prediction. Planned A/U in [SAMPLE_PLAN.md](SAMPLE_PLAN.md) are hypotheses until this check. Actual dispatch, consumption, sink disclosure and task completion have separate observed fields. A no-grant send after source exposure may be UNAUTHORIZED under the scoped/conservative contract while delivering no sensitive bytes.

## Separate task-level client objective acknowledgment

The current pilot has per-tool `client_responses.json` and sink acknowledgments, but no task-level client objective acknowledgment. The proposed new record is **one independently held, append-only record per parent**, emitted by the scripted client/assessor observer only after all predeclared tool attempts and the final objective output/failure are observed. It is not a new MCP `tools/call` response and must not be inferred from child/host closure or a successful send.

Minimum canonical fields: schema/version; run challenge and frozen-plan digest; block, parent, run, task and session IDs; client/observer ID and pinned verifier key ID; objective ID and exact expected-output digest; ordered planned and attempted case IDs with request/response hashes and outcome statuses; final client-visible output bytes (or explicit absence) and SHA-256; objective status `COMPLETE`/`INCOMPLETE`/`UNKNOWN` with a predeclared criterion and reason; source/sink receipt references and their hashes; last observed sequence/order marker; acknowledgment event ID and local observation time (advisory only); observer signature over the canonical record, using a separately pinned P-256 public key or an equivalently approved assessor-held integrity mechanism. The private key stays outside the package. The acknowledgment is bound to the parent and challenge, not merely to a case name or a tool response. An assessor-held post-run index may bind the acknowledgment digest to the signed package digest without a circular signature.

Ordering to verify: freeze objective/plan/challenge and register parent → open task → observe all declared calls, controls, outputs and failures → client computes final objective state → emit and durably retain acknowledgment → close/verify child, host and sink streams → seal/export signed evidence → independently inspect package and acknowledgment, then verify their ID/challenge/digest linkage. The observer must be trusted under the stated local harness boundary; a client statement alone cannot prove sink delivery, and a signature authenticates the statement, not its truth. The assessor checks its claimed output against raw client bytes and independent sink/file receipts. If the client crashes, times out, retries, omits the final output, or cannot sign/durably retain the record, preserve a failure/absence record; parent completion is UNKNOWN or INCOMPLETE per frozen criterion and **E03 full-contract qualification fails**. Never synthesize an acknowledgment after the fact.

The minimum future change is an assessor-held task acknowledgment writer at the scripted-client boundary plus a **fresh-process** validator that checks schema, signature/key pin, exact identity/challenge/objective binding, one-record uniqueness, ordering, observed output bytes/digests, references, and closure/export linkage. It can be a research collector/verifier companion; no alteration to the locked MCP protocol or application security policy is proposed here. Whether any application integration is needed must be determined during approved implementation review. The current collector has no executable capture/verification path for this task-level record.

## Per-case evidence and validation contract

For **every** planned call (including malformed control), retain the frozen contract and immutable case-to-parent/label mapping; exact raw request and response bytes plus SHA-256; client submission/return/exception and retry ledger; host admission/dispatch/reservation-control witnesses; complete child handler stream with closure; sink stream with exact payload bytes/base64, byte count, SHA-256 and closure; signed export and fresh-process offline-verifier dimensions. Sensitive source cases additionally require child source arrival, exact controlled result and client-visible result; exposure is UNKNOWN without a successful result witness. Sends require a destination-tagged receipt or a *closed, complete* sink capture for non-arrival. A positive arrival counts even if expected denial; no-arrival is not inferred from a missing row in an open stream. For a denied or failed read, retain schema/error status, no-handler coverage and absence of source acquisition. For authorized release, retain exact host grant scope and confirmed commit before the proposal; unconfirmed commit yields INDETERMINATE authorization. Task-level acknowledgment and objective evidence are required per parent, with case links to it.

Missing/ambiguous source, commit, raw request, task identity, assessor label, capture closure, signed package, offline verification, or task acknowledgment cannot be converted into a favorable binary outcome. A malformed call remains a control outside the detector denominator if it is genuinely rejected before proposal. Unexpected forwarding or sink arrival remains an observed adverse effect. A missing task acknowledgment invalidates parent completion and E03 full-contract status; detector rows, if otherwise sound, may only be reported as descriptive, contract-incomplete observations. Preserve all failures, retries, timeouts, invalid/excluded cases and the exact reason/denominator.
