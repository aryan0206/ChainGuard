# H6–H9 live qualification readiness — entry point and witness contract

Read-only source inspection on 2 November 2026. No Git command, test, live workflow, or E01–E13 experiment was run in this checkpoint. Proposed changes below are **not implemented or approved**. The eight case expectations remain those frozen in `../H2-H6/qualification_plan.json`.

## A. Revision lookup and no-Git entry point

`M6Host.open_task` in `chainguard/m6_live_runtime.py` calls `live_configuration()` and passes its result to `make_live_manifest`. `live_configuration()` in `chainguard/m6_live_profile.py` runs `git rev-parse HEAD`, computes installed artifact SHA-256 digests, and builds the policy, registry, normalizer, detector, and controller configuration. `make_live_manifest` calls `validate_live_configuration`, which calls `live_configuration()` again; `validate_live_manifest` repeats that validation. The live audit constructor also validates the manifest. `HostTask.export_live_evidence` validates the manifest again before sealing. Offline `inspect_live_package` and `inspect_live_run` validate the assessor's expected configuration against the locally installed configuration. Live acceptance validation in `chainguard/acceptance.py` calls the same validator. Thus the no-Git issue is present at open, export, offline verification, and acceptance, not just at the first call.

The revision is a **provenance and configuration-binding field**, not an authorization input or cryptographic secret. Architecture Lock Section 9 requires it in the signed manifest together with artifact digests. The code checks exact agreement between the package configuration, independently supplied expected configuration, and installed configuration. The 40-hex revision value alone does not prove the working tree matches that revision; artifact digests identify the actual installed files. A read-only `rev-parse` does not mutate Git state, but the sprint explicitly prohibits executing Git commands, including this internal lookup.

There is no supported explicit revision input end to end. `make_live_manifest(inventory, config, ...)` accepts a configuration object, and export/verifier APIs accept `expected_configuration`, but their validators recompute the installed configuration through `live_configuration()` and therefore invoke Git. Injecting a configuration in a wrapper or monkeypatching the lookup would change the qualified path and would not solve offline verification/acceptance.

**Smallest safe proposed source change for owner review:** replace the Git lookup in `live_configuration()` with a mandatory, trusted host-provisioned 40-character lowercase hexadecimal revision input, fail closed when it is missing or malformed, and retain computation of all installed artifact digests. A narrowly scoped environment variable is the smallest code surface because all existing call sites use that function; it must be set by the trusted launch/assessor process before open, export, verification, and acceptance, with its source retained independently of the package. No fallback to Git should remain in the no-Git path. The verifier must compare the package with a separately pinned expected configuration and installed artifact digests; it must not adopt the revision from the submitted package. An explicit constructor/context parameter would make trust provenance clearer but would touch more call sites.

Affected source: `chainguard/m6_live_profile.py` (mandatory revision provider and validation). A trusted launch configuration/assessor record is also required. Relevant tests to update or add: live profile, evidence, audit, runtime, seal, verifier, and acceptance tests, including missing/malformed revision, wrong independently pinned revision, artifact mismatch, and an assertion that open/export/inspect/accept make no Git subprocess call. The change adds no dependency and changes no cryptographic algorithm or architecture field. Security cost: a host environment value is an assertion, not proof of Git HEAD; it is safe only under the existing trusted-host assumption and independent assessor pinning. The report must describe that provenance limit. No source or test edit is authorized in this checkpoint.

## B. Case and witness binding rule

Before any live execution, the assessor must freeze case ID, run ID, random challenge, task/session/monitor IDs, expected grant IDs/scopes, raw request IDs and bytes, expected source canary, destination, task objective, signer key ID/public-key pin, and expected configuration. The assessor journal must be outside the simulated audit database and must use a local monotonic record number, observed local time for diagnostics only, and a digest of each raw capture. Match request IDs to case IDs through this prewritten mapping; match grant IDs/scopes and task/session IDs across control/commit witnesses. Check ordering by assessor journal sequence and confirmed completion boundaries, not by timestamps alone. Preserve capture gaps as UNKNOWN. This is a proposed witness collection contract, not an existing H6–H9 observation.

## C. Witness inventory and gaps

### 1. Grant/revoke source and commit

- **Producer/current fields:** trusted host calls `HostTask.grant(grant_id, Scope)` or `revoke(Scope)`; `admissions` has `(ticket, kind, grant_id)` and the Future resolves without a detailed result. Audit records contain grant/revoke details, but copying them would be circular.
- **Independence and content:** an assessor can retain the issued host command before submission, with exact grant ID/scope bytes or digest. A successful Future indicates the worker finished the control path after a confirmed append, but the current API does not expose a separate commit receipt to the assessor. The internal `LiveCommitReceipt` includes session ID, first/last seq, batch/count, final head, event IDs and types; it is consumed inside the authority.
- **Required path:** independently record issued control, queue admission, and a trusted callback/receipt at the confirmed transaction-completion boundary, including grant ID/scope and journal sequence. Bind to case/run/task/session and check FIFO order. If the receipt is absent or ambiguous, permission state is UNKNOWN; do not infer success from a later SQLite row. Supports pre-decision authorization and revoke/regrant claims only once collected.

### 2. Raw proposal

- **Producer/current fields:** assessor/scripted client can retain exact JSON-RPC request bytes before `_submit_client_frame`: ID, method, tool name and arguments, including payload. This is independent of normalized audit findings. The host also retains limited admissions `(ticket, CALL_PROPOSAL, request_id)`.
- **Required path:** write bytes and SHA-256 to assessor journal before submission, with case ID and expected run/session mapping. Use raw bytes to label the proposed operation; do not reconstruct proposals from audit rows. Missing raw bytes makes pre-decision labels INDETERMINATE. Supports authorization/oracle attribution, subject to control/source evidence.

### 3. Handler invocation and child startup/failure

- **Producer/current fields:** child server stderr JSON `tool_received` has component, phase, request ID, tool, child PID and parent PID. Startup uses a child process and `server/discover` then `tools/list` over stdio, but no complete raw startup/handshake trace is retained. Non-JSON stderr is discarded by the host reader. `HostTask.child_events` is a host-mediated copy, not an assessor-held raw child stream.
- **Required path:** assessor-owned raw child stdout/stderr/process observer or separate side channel, with child PID, start/exit, raw handshake frames, monotonic receive sequence, request ID, run/session mapping, and capture-closure record. A `tool_received` record supports actual handler arrival; absence supports non-arrival only when the collector was alive through clean child termination and the complete stream was retained. Startup failure without this trace remains unresolved. The child PID is correlation, not authentication against a compromised host.

### 4. Sink arrival and exact content

- **Producer/current fields:** child emits `m6_local_sink/sink_arrival` with request ID, tool, destination and UTF-8 `payload_byte_count`. It emits no payload bytes or digest and has no independent timestamp. The raw request contains intended payload, but that does not prove received content.
- **Required path:** a separate assessor-controlled local sink/capture channel records destination, request ID/case mapping, actual received bytes or SHA-256 of actual bytes, byte count, and receipt sequence. Its collector must attest complete observation through task closure for a negative result. A payload digest can establish equality to the frozen synthetic canary under the stated capture boundary; the existing byte-count event can support only bounded arrival metadata. No current source proves exact disclosure or independently witnessed non-arrival to the locked standard.

### 5. Reservation/consumption and dispatch

- **Producer/current fields:** `LiveAuthorizationTask.admit_call` plans a grant set and appends proposal/findings/decision/intent as one batch; after confirmed append it removes selected active grants and returns a `DispatchPermit`. `_write_downstream` calls `take_dispatch` then writes to child stdin. `LiveCommitReceipt` is internal; the signed record's `selected_grants` is evidence under evaluation, not an independent witness.
- **Required path:** assessor-held observed commit-boundary receipt with call ID, request ID, exact selected grant IDs/scopes, sequence/head and success/ambiguity status; separately retain attempted downstream write and handler arrival. If commit acknowledgement is unavailable, consumption is UNKNOWN. Receipt equality to audit data is a consistency check, not oracle provenance. Supports one-use/no-refund/all-or-nothing attribution only after independent capture.

### 6. Task outcome

- **Producer/current fields:** the client receives a JSON-RPC result or error; the send result is a fixed local-sink acknowledgement. This is a response, not independent proof of task completion. Source reads return synthetic text in the client response; the handler event does not include result bytes.
- **Required path:** assessor-held objective and independently captured client output plus destination receipt or output artifact, keyed to case/request and ordered after handler arrival. Missing task output remains UNKNOWN; denial/error cannot automatically be counted as legitimate completion or failure. Supports task-completion/disruption claims only for predeclared objectives.

### 7. Signed export and offline verification

- **Producer/current fields:** after confirmed clean close, `export_live_evidence` freezes/reconciles audit snapshot and writes a canonical package exclusively, including manifest, ordered records, commitment and P-256 signature. Offline `inspect_live_package` reports package schema, chain/closure, trusted signature, expected binding, inventory, lifecycle, and finding reproduction dimensions.
- **Independence and use:** the package is produced from the audit pipeline, so it is **not** an independent source/sink/consumption witness. The verifier is independent only when inventory/challenge, expected configuration, and public-key pin are retained outside the package. Verify chain order and signature with the pinned key; compare to assessor witness journal separately. Failure or missing clean close is incomplete or rejected as specified, not proof of attack. Supports evidence-integrity/reproduction claims, never detector correctness or actual tool effects by itself.

Current gaps needing owner-approved implementation or collection design are the no-Git revision input, assessor-held commit-boundary receipts, raw child startup/handler stream and complete capture closure, actual sink bytes/digest, and independent task-output criteria. These are not resolved by existing passing engineering tests.
